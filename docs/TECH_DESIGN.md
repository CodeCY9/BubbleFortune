# BubbleFortune 技术设计

更新：2026-09-12。需求依据：[GDD](../GDD_V2.0.md)。进度与验收依据：[ROADMAP](ROADMAP.md)。本文件记录 V0.1–V1.0 的实现约定；V0.3、V0.4 与 V1.0 业务代码已交付，完成状态仍以验收证据为准。当前统一结论是“业务实现已覆盖，发布验收未完成”。

## 当前事实

- 根项目保留 Vite/React/TypeScript；[游戏服务端](../apps/game-server/src/server.ts) 使用 Node.js/TypeScript + Colyseus，公开协议位于 [packages/protocol](../packages/protocol/src/types.ts)。
- [useGameState](../src/hooks/useGameState.ts) 已接入服务端快照和命令；[表现层](../src/utils/presentationManager.ts) 控制动画揭晓，不计算结果。功能验证见 [本轮验收](validation/2026-09-10-server-single-player.md)。
- 保留 [Box3D](../src/components/Box3D.tsx) 的 v009 箱子与 [StageEnvironment](../src/components/StageEnvironment.tsx) 的 v007 舞台；模型性能的历史证据与本轮网络迁移验收分开记录。
- 启动入口为 `npm run dev`，同时运行 Vite 3000 和游戏服务端 2567；浏览器经同源 `/game` 代理访问 HTTP 匹配接口与 WebSocket。本轮新增独立 `duel_26` 双人房间及双人历史接口，加入可选私密房密码、公开列表开关、延迟探测与显示；公开列表只返回人数、排名资格和密码要求等安全摘要；密码房会写入 `isPrivate=true`、`ranked=false`，只保存历史不更新正式 Elo。业务交付状态见 ROADMAP，真实验收仍待执行。

- 主题运行时白名单通过公开的 `GET /api/themes` 下发，响应只包含主题 ID 和当前激活主题；管理员修改不会进入游戏规则，客户端在局中继续受 PWA 更新锁定。
- AI 头像资源：`RoomLobby` 与 `BankerModal` 使用五种 AI 的独立 2D 表情映射，`scripts/build-pwa.mjs` 将六套资本家 PNG 纳入运行时资源白名单；图片只用于表现，不进入服务端报价、金额或角色裁决。
- 房间创建时可提交白名单 `themeId`（`classic` 或 `starry-neon`）；`duel_26`、`auction_26`、`survivor_26` 与 `tournament_26` 服务端会锁定并写入元数据，再从本人/公共快照同步给参与者和观战者。主题只改变资源、颜色、灯光和低画质回退，不改变金额、轮次、随机映射、报价或排名；加入已有房间时客户端不得以本地主题覆盖权威快照。
- `duel_26` 与 `auction_26` 的报价历史公开开关只控制公共实时投影；关闭时客户端收到空历史数组，服务端仍保留完整审计和参与者历史详情，且不改变报价裁决。
- 风控只持久化 `BF_RISK_SECRET` 派生的 IP 与请求头指纹，不记录原始地址或用户代理；对决/竞拍/生存战/锦标赛结算后，仅在共享指纹且 24 小时内完成至少 5 场固定对手时自动生成 `MATCH_FIXING` 排除标记，管理员仍可人工复核和解除。
- 排行榜公开查询支持白名单 `board` 维度（综合 Elo、累计净利润、角色收益、胜率、生存战胜场、锦标赛胜场、完成局数、单人最高收益和单人最佳成交差额）；排序字段由服务端固定拼接，风控隔离玩家在所有榜单中排除，客户端不得提交任意排序 SQL。
- 对决和竞拍结算还会在服务端审计结果中识别窄范围的让利信号：同一固定对手组合在至少两轮出现高于箱值的成交报价且资本家负收益时，追加独立的 `automatic-concession-v1` 标记；该标记只影响排名资格和后台复核，不改变已完成对局结果，也不把隐藏金额或内部判断发给客户端。
- 舞台性能策略：移动端和节能档关闭实时阴影/环境贴图，标准档使用 1024 阴影贴图且仅选中或正在开箱的箱子投射阴影；设置页还提供触感、闪烁、景深、屏幕摇晃、高对比度和色弱友好显示控制；报价倒计时最后 5 秒由 `soundManager.playCountdownWarning` 提供一次/秒的声音反馈，并遵循本机声音开关；该策略尚未替代真实设备基线。

- 单人榜单：`DatabaseManager.getRankings` 对 `single_highest`/`single_margin` 使用 `completed_games` 的权威结算记录，并与选定赛季的起止时间、该赛季风险排除状态和分页条件联接；返回只含聚合分数，不暴露金额映射、审计秘密或游客身份。
- 游客资料：`getProfileSummary` 从游客自己的 `completed_games` 中按 `classic-26-v1` 聚合单人场次、最高 `wonAmount` 和最高 `acceptedOfferAmount - originalBoxAmount`，资料接口与弹窗只展示汇总值；缺少成交记录时最佳差额返回 0，保持旧资料响应字段兼容。

## 当前范围与实施约定

V0.1 的规则、服务端与现有 3D 界面已接通，真实设备性能仍需验收；按已批准路线图推进 V0.2 设置、公平校验、游客战绩、三种 AI 与 PWA/分享。各功能验收独立记录，不以代码存在代替完成。

GDD §6.4 的五种 AI 已接入服务端 `ai-v1` 策略和游客选择界面；报价会根据服务端维护的本局拒绝、接受和超时摘要生成白名单对白，诱导型/疯狂型可使用摘要调整策略，客户端不接收 EV、倍率或内部参数。既有离线模拟证据仍只覆盖基础三种，新增行为和对白保持待验证。

前端沿用现有 src/，业务接口复用 Node/Colyseus 服务；PostgreSQL 只保存游客身份、已完成对局与分享摘要。暂不引入 Redis、独立业务服务、账号或跨设备同步。

V0.4 的 `auction_26` 使用服务端固定 1,000,000 虚拟资本、每人一次密封第一价格报价、同价按接收序号胜出；每名玩家轮流担任一次挑战者。观战最多 4 人，只接收公共快照和公开事件。竞拍命令沿用状态版本、命令序号和幂等键，私密报价、可用资本和未开箱金额只进入本人投影。

`tournament_26` 的房间创建时固定 `format: duel | survivor`。每场子对局只接收对应的 `duelCommand` 或 `survivorCommand`，快速生存战两席由服务器自动开始并在子对局结束后映射为晋级胜者；公共锦标赛快照同时保留格式和对应子对局公共投影。双方最高分相同时使用 `sha256-match-seat-v1` 单次服务端裁决，晋级树、终局结果和审计记录带有 `tieBreakUsed` 标记。

V1.0 的排名使用 UTC 四周赛季、Elo 1000/K32。双人按胜负更新，多人按最终名次成对比较；私密房、未完成局或任一参与者存在有效风控排除时整局不计入正式 Elo。管理员接口使用环境令牌换取短期 HttpOnly 会话，令牌不进入前端存储；主题仅改变资源、颜色、灯光和低画质回退，不改变玩法结果。

公开/私有投影分离：隐藏逻辑放服务端内部，不放前端可导入的聚合导出中。接口与故障约定见 [V0.2 运行协议](specs/v02-runtime-contract.md)。PWA 仅提供静态应用壳与安装能力，正式对局始终联网。游客成就写入 `guest_achievements`（迁移 8），生存战/锦标赛模式统计写入 `ranking_profiles` 扩展字段（迁移 9），对决/生存战/锦标赛公开分享索引写入 `multiplayer_shares`（迁移 10），服务端分析事件写入 `analytics_events`（迁移 11）；回放、分享和分析接口只返回参与者或管理员有权读取的公开聚合与审计白名单，不返回新的秘密字段。

## 服务端状态机

| 阶段 | 合法意图 | 服务端动作 | 下一阶段 |
|---|---|---|---|
| SELECTING | select_box | 锁定合法个人箱 | OPENING |
| OPENING | open_box | 揭晓合法非个人箱、扣本轮次数 | OPENING / OFFERING / FINAL_SWAP |
| OFFERING | accept_offer / reject_offer | 校验报价、成交或准备下一轮 | FINISHED / OPENING |
| FINAL_SWAP | keep_box / swap_box | 揭晓并生成唯一结算 | FINISHED |
| FINISHED | 只读结果/校验请求 | 返回已生成结果，不重复结算 | FINISHED |

开满 24 箱后进入 FINAL_SWAP，不再创建报价。动画阶段不是裁决状态；断线为连接状态，不重置对局阶段。

超时采用 GDD §8.3：选个人箱 30 秒随机合法选择，开箱 20 秒随机合法选择，AI 报价决策 30 秒默认拒绝，最终选择 30 秒默认保留。所有超时在服务端裁决，客户端时间仅作体验统计。双人人类报价限时 25 秒、挑战者决策限时 30 秒，见下方对决约定；资本竞拍另行实现。

| 数据 | 服务端内部 | 公共视图 | 玩家私有视图 |
|---|---|---|---|
| 未公开箱子金额、种子、盐、报价参数 | 是 | 否 | 否 |
| 箱号、公开状态、已揭晓金额、轮次、截止时间 | 是 | 是 | 可引用 |
| 私密报价、可操作项、资本家合法报价区间 | 是 | 按模式禁止泄露 | 仅有权限者 |
| 最终校验证据 | 是 | 整局结束后按规则公开 | 不可提前获取 |

服务端以白名单投影生成 DTO，不序列化完整内部对象后再尝试删字段。未开箱没有 amount/revealedAmount；网络错误、快照、观战和日志回传使用同一隔离规则。合法操作由服务端给出，但收到命令仍需重新校验。

## 协议约定

命令含房间/会话关联、stateVersion、commandSequence、idempotencyKey、意图与参数。会话身份由连接验证，不信任载荷里的 playerId。响应关联幂等键，返回成功/错误、权威版本及允许公开的状态。

- select_box/open_box/swap_box 只传目标箱号；accept_offer/reject_offer 传 offerId；不由客户端传权威结果。
- 相同身份与幂等键的相同载荷返回同一处理结果；相同键不同载荷拒绝。先识别已处理重试，再判断旧版本，避免成功重试误报冲突。
- 每房间串行处理状态变更；超时事件和玩家命令走同一裁决路径。结算有唯一结果标识，数据库同时约束 result_id 和 game_id；重复记录必须核对身份与完整内容，冲突记录隔离而不覆盖。
- 错误类别至少覆盖未授权、非法阶段、非法箱子、版本冲突、报价过期、幂等载荷冲突和会话失效；不带秘密内部信息。
- stateVersion 单调推进；客户端丢补丁或重连时取当前授权快照，不依赖播放历史事件恢复。

## 结算与随机校验

接受有效报价：玩家收益为服务端报价；最终保留/交换：收益为最终归属箱金额。记录原始个人箱、最终个人箱和成交报价，避免交换后丢失原始选择。结算生成一次，动画或重复请求不能再次改变收益。

新局使用独立的 32 字节安全随机种子与盐，SHA-256 承诺和带版本的 HMAC-SHA256 Fisher–Yates 洗牌；规范编码、域隔离及固定向量见 [fairness-v1](specs/fairness-v1.md)。只在 FINISHED 公开种子、盐、映射及有序事件链。浏览器使用共享的 WebCrypto 验证器复算；只有本机在终局前见过且保存了匹配的开局承诺，才能显示与开局承诺一致。仅有终局数据时明确标为自洽校验，旧记录无证明则不支持校验。

事件链提供完整性核对，不称为不可篡改；服务端仍是记录发布方。多回合不得复用已公开种子，日志与错误不得提前回传秘密。

## 游客战绩与持久化

- `/api/guest` 区分未配置数据库、数据库暂时不可用和身份状态。游客通过独立的 HttpOnly、SameSite=Lax Cookie 识别；生产环境要求 Secure/HTTPS，凭据在数据库中仅存哈希，不复用房间重连令牌。
- `/api/history` 和详情按游客隔离；无权限与不存在统一返回 404。完成记录保存规则、AI 版本、报价历史、决策事件和公平证据，历史在服务重启后保留；进行中会话仍不恢复。
- 终局先原子写入本地 `.data/history-outbox/` 并刷新到磁盘，再重试写入 PostgreSQL。数据库故障不会生成第二份收益；损坏、身份或内容冲突进入隔离目录。部署时必须持久保存数据库卷和 outbox 目录。
- 所有身份、历史及分享 API 响应使用 `Cache-Control: no-store`。分享必须由用户主动创建，公开接口只返回已结算摘要白名单，不公开游客凭据、私人战绩列表或完整事件。
- 未配置数据库可进行无战绩权威游戏；已配置但身份服务故障时不得偷偷创建匿名身份或新局。已进行的对局可继续裁决，历史待数据库恢复后补写。

## 表现、资源与恢复

前端只保存授权快照、本地请求等待与表现状态。收到服务端确认后才播放揭晓；同一时刻只能开一个箱子。对应金额栏、顶部已开箱记录、报价和最终选择等待动画完成再更新。超时导致多个揭晓时顺序表现，初次连接与重连则直接恢复当前局面，不重播历史动画。3D 失败保留 HTML 操作或明确重试入口；游戏不得自动切成本地随机模式。资源规范见 [DESIGN](../DESIGN.md) 与 [ASSETS](ASSETS.md)。

重试沿用原请求的幂等键与完整载荷；响应按幂等键关联，旧响应不能解除新请求的等待。服务端拒绝时同时返回当前公共快照，客户端据此恢复合法操作。重连令牌只用于恢复原席位，不作为箱子金额存档；暂时重连失败保留令牌供再次尝试，新局由明确的重新开始操作创建。

- 采用 [duel-26-v1](specs/duel-26-v1.md)，独立引擎与公开协议，不改变 Classic 单人引擎的命令和 AI 行为。两回合分别发布承诺，整场结束后才公开已开始回合的证明。

- 挑战者选箱、开箱、处理报价与最终选择；资本家只能在本人允许操作时提交整数报价。合法区间仅发资本家，内部平均值和报价系数留在服务端。

- 上一轮 V0.3 交接曾按当时要求只提交业务实现，因此对决设备、网络和秘密隔离证据仍不能由代码存在替代；当前 V0.4/V1.0 回归命令与限制统一记录在 [最新验收记录](validation/2026-09-11-v04-v10-working.md)。
